# 汎用 RAG 設計ガイド（reference）

/arch-design で RAG 系の設計ノードを分解・決定する際の参照マニュアル。
**会社プロジェクト固有情報は含めない。あくまで汎用パターン**（方式・評価・トレードオフ）。

決定解決ループ（SKILL.md Phase 2）の中で、未決定ノードの**候補・トレードオフ**を洗い出すための材料。
ここに書いた選択肢をそのまま Best of N の選択肢シート（FORMS #3）へ展開する。

---

## 1. RAG の全体構成（ノード分解の起点）

```
質問
  └─ 1. 検索クエリ整形（クエリ拡張 / 分解 / rewriting）
        └─ 2. 候補検索（retrieval）: 密度・語彙・ハイブリッド
              └─ 3. 再ランク（rerank）: 交差エンコーダ / LLM 判定
                    └─ 4. 文脈組み立て（top-k / 重複除去 / 長さ制御）
                          └─ 5. 回答生成（生成 + 根拠付与）
                                └─ 6. 確信度・抑制（不確実なら回答しない）
```

各段階が「決定ノード」。設計時に次の粒度で分解すると扱いやすい:
- 検索方式 / 埋め込みモデル / 再ランク有無 / top-k / 確信度閾値 / 評価セット / 運用監視

---

## 2. 候補検索（Retrieval）— Best of N

| 案 | 方式 | 利点 | 欠点・トレードオフ |
|----|------|------|--------------------|
| A | ベクトル検索（埋め込み×コサイン） | 意味的な類似に強く、言い換え耐性が高い | 埋め込み生成コスト・初期データ必要・語彙の厳密一致（ID・番号）に弱い |
| B | キーワード（BM25） | 実装軽量・解釈容易・語彙一致に強い | 意味一致に弱く、言い換え・同義語に不利 |
| C | ハイブリッド（A+B の融合） | 意味×語彙の両補完。精度が安定 | 重み調整と再ランク実装が複雑 |

- 融合重みは固定でなく、評価セットでチューニング（例: RRF / 線形加重）。
- 語彙ミスマッチ・固有表現・ID検索が主用途なら BM25 単独でも十分な場合がある。

---

## 3. 埋め込みモデル選定の判断基準

- **判別タスクでの対比較衡量**: 埋め込みモデル単体性能より、選択後の`検索→再ランク→生成`の E2E で測る。
- 評価基準: 汎用埋め込みベンチを軸に、**自データで recap@k** を採る（後述）。
- トレードオフ: モデルサイズ・次元数 ↔ 検索速度・コスト・運用負荷。
- 決定時は「モデル名と理由・却下案」を決定ログに残す（固定化）。

---

## 4. 再ランク（Rerank）— 入れるか入れないか

| 判断 | 概要 | トレードオフ |
|------|------|------------|
| なし（そのまま top-k） | 検索スコア順で文脈化 | 実装最小・高速。ただし検索の雑音が回答に乗りやすい |
| 交差エンコーダ再ランク | 質問×文書を Deep Model で対で判定 | 精度向上。追加コスト・レイテンシ |
| LLM 再ランク | 生成系 LLM に 1 件ずつ判定させる | 汎用性高い・遅い。小問題には過剰な場合も |

- 高品質回答が必要でコスト許容なら再ランクを入れる。小規模・低コスト優先なら省略。
- **top-k**: 多いほど文脈が富むが、雑音とコストが増える。評価セットで「k を増やしても効果が頭打ちになる点」を見て決める。

---

## 5. 文脈組み立て

- **重複除去（dedup）**: 同一内容の断片が複数ヒットする場合、冗長化を防ぐ。
- **長さ制御**: モデルの文脈窓と入力トークン数を監視（過積載は性能劣化の原因）。
- **順序**: 信頼度の高い断片を文脈の先頭に置くと生成質が上がる傾向（Lost in the Middle 対策）。

---

## 6. 確信度キャリブレーション（不確実なら回答しない）

RAG の失敗モード（根拠なき回答・幻覚）を防ぐ仕組みを設計時に決める。

| 指標 | 概要 | 使い方 |
|------|------|--------|
| 検索スコア | 候補の検索距離/類似度 | 低すぎる場合に「根拠なし」と判定する閾値化 |
| 再ランクスコア | 質問×断片の適合度 | 閾値以下は文脈に含めない |
| LLM 自己申告 | 生成時の根拠の有無・自信 | 「根拠が見当たらない」応答の許可 |
| 引用存在チェック | 回答中の主張が検索断片由来か | 引用が張れない主張は抑制 |

- 設計時に **閾値** を数値で定める（曖昧語禁止の原則）。例: 「確信度 < 0.5 なら『根拠なし』と明記して回答しない」。
- 閾値は初期値とし、運用データで調整する（後述の評価ループ）。

---

## 7. 評価指標（Evaluation）— 設計時に決めておく

RAG の品質を測る指標。**設計開始時点で評価セットを用意しておく**ことが、全ノードの決定を検証可能にする。

| 観点 | 指標 | 意味 |
|------|------|------|
| 検索 | recall@k / nDCG@k / MRR | 必要な文書が上位に来るか |
| 生成 | 根拠一致率・引用付与率 | 回答が断片に裏付けられているか |
| 回答 | 正確性・有用性（人手/LLM-as-judge） | 場当たりでない、実際に役立つか |
| 失敗 | 幻覚率・「根拠なし」の適切抑制率 | 間違いを減らせているか |

- **評価セット**: 実運用に近い質問 100 件程度 + gold 回答/関連文書。最小構成で始めて回す。
- **LLM-as-judge**: 人手評価が高価な場合の代替。判定モデルのバイアスには注意（判断基準を明文化）。

---

## 8. 運用モニタリング

- 回答の**根拠引用率**・**「根拠なし」応答率**・検索 hit 率をログし、傾向を監視。
- 実ユーザーからの検索ゼロ件・低確信度を**失敗サンプル**として回収 → 再ランク・閾値・埋め込みの改善に回す。
- **改善ループ**: 評価セット更新 → 検索/再ランク/閾値の再チューニング → リグレッション確認。

---

## 9. 設計時のチェックリスト

- [ ] 評価セット（質問 + gold 回答/関連文書）を用意した
- [ ] 検索方式を Best of N で決定し、理由・却下案を決定ログに残した
- [ ] 埋め込みモデル・再ランク有無を E2E の成功基準で決定した
- [ ] top-k・確信度閾値を数値で定めた
- [ ] 「根拠なき回答の抑制」の方針を明文化した
- [ ] 評価指標（recall@k・根拠一致率・幻覚率）を定義した
- [ ] 改善ループ（失敗回収→再チューニング）を設計した
