# /arch-design — アーキテクチャ・アルゴリズム設計（決定解決ループ）

## 概要

設計対象を **ノード** に分解し、各ノードの決定を「決定済み / 未決定」に峻別する。
未決定ノードだけをリサーチ→ **Best of N** で選択肢化→ **人間決定（AskUserQuestion）** →固定化、
という **決定解決ループ** を回す。最終的に **低認知負荷ドキュメント**（結論先行・表/mermaid・曖昧語禁止）
と **実装計画書（簡易ロードマップまで）** を出力する。

**独自価値（既存スキルと包含されない2点）**:
1. **決定解決ループ** — 決定済み/未決定の峻別 → 未決定をリサーチ → 人間決定 → 固定化
2. **低認知負荷文書** — 結論先行・表/mermaid・曖昧語禁止・未決定バックログの常時最新化

---

## ワークフロー（Phases 0〜4）

```
設計依頼
  ├─ Phase 0 状況把握（ゴール・制約・既存資産の確認）        [Auto-Exec]
  ├─ Phase 1 ノード分解（設計対象を決定ノードの木に分解）
  ├─ Phase 2 決定解決ループ（未決定ノードを順に解決）★
  │        └─ 決定済み固定化 → リサーチ → Best of N → AskUserQuestion → 固定化
  ├─ Phase 3 低認知負荷出力（結論先行の設計文書を生成）
  └─ Phase 4 実装計画書（簡易ロードマップ。詳細WBSは /impl-doc 委譲）
```

出力先: **Obsidian `${OBSIDIAN_VAULT}/00-Inbox/`**（`YYYY-MM-DD_<件名>_設計書.md`）。本文は設計成果物の正。プラン残骸は作らない。

## Phase 0: 状況把握（Auto-Exec）

- 設計の **ゴール** と **成功の定義** を1文で確認（弱い成功基準のまま進めない）。
- **制約**（技術・コスト・人員・期限）と **既存資産**（再利用できるコード/ライブラリ/決定）を列挙。
- 会社プロジェクト固有情報が含まれる場合は、それを持ち込まない（汎用コアに徹する）。

## Phase 1: ノード分解

設計対象を、決定が必要な **ノード** の木に分解する。

- 例: システム全体 → データモデル / 検索方式 / レイテンシ要件 / 規模想定 / 運用方式 …
- 各ノードに **状態ラベル** を付ける:
  - ✅ 決定済み（固定化済み・再検討しない）
  - ❓ 未決定（リサーチと人間決定が必要）
  - ⚠️ 依存（別ノードの決定に従属）
- 分解の粒度は「1ノード=1人が1回で判断できる」程度に保つ。深くなりすぎたらサブノード化。

成果: **ノード分解表**（FORMS.md 参照）。

## Phase 2: 決定解決ループ ★（本スキルの核）

未決定ノードを **1つずつ** 以下のループで解決し、固定化していく。

```
[決定済み?] ──Yes──▶ 固定化（記録のみ）
     │No
     ▼
1. そのノードの判断基準（何が「良い決定」か）を明文化
2. リサーチ（必要時のみ）: 候補の事実・トレードオフを収集。ソース無き主張は「未検証」
3. Best of N: 候補を2〜3案生成し、各案の利点/欠点/トレードオフを表で対比
4. AskUserQuestion: 人間に決定を委ねる（推奨案を先頭にし理由を付す）
5. 固定化: 決定ログに「決定・理由・却下案」を記録し、以降は再検討しない
```

**原則**:
- 1ループ=1ノード。複数の未決定ノードを混ぜて同時に判断させない。
- 曖昧な点は勝手に解釈せず、前提を宣言して確認する（karpathy: Think Before Coding）。
- 決定の一覧は **決定ログ** に蓄積し、後で「なぜこの方式にしたか」を再現できるようにする。

成果: **決定ログ**（決定・理由・却下案）+ **未決定バックログ**の更新（FORMS.md 参照）。

## Phase 3: 低認知負荷出力

固定化した決定を、読者が追いやすい **低認知負荷ドキュメント** に整形する。

**原則（低認知負荷）**:
- **結論先行**: 各セクション冒頭で結論を述べ、根拠は後。
- **一文一意**: 1文に1つの事実。長い接続文・二重否定を避ける。
- **表 / mermaid 多用**: 対比・フローは文章より表と図。連続散文で説明しない。
- **曖昧語禁止**: 「〜の方が良い」「〜ほど」「適切に」「いい感じに」等を禁止。数値・基準に置き換える。
- **未決定バックログ**: 未解決ノードは冒頭に可視化し、常時最新化する（隠さない）。

成果: **設計書テンプレ**（FORMS.md 参照）に沿った Markdown を Obsidian `${OBSIDIAN_VAULT}/00-Inbox/` へ出力。

## Phase 4: 実装計画書（簡易ロードマップ）

設計書をもとに、実装の **簡易ロードマップ（マイルストーン・順序）** までを本スキルで生成する。

- 含める: フェーズ分割・各フェーズの完了判定・依存順序・主なリスク。
- **詳細WBS（タスク分解・見積り・依存テーブル）は `/impl-doc` へ委譲**（機能重複を避ける）。

（実装計画の深掘りが必要な場合は、出力後に `/impl-doc` を起動して詳細WBSへ進む。）

## 決定解決ループ と 低認知負荷 の要点（再掲）

| 観点 | 原則 |
|------|------|
| 決定 | 1ループ=1ノード。Best of N→人間決定→固定化。却下案も記録 |
| 文書 | 結論先行・一文一意・表/mermaid・曖昧語禁止 |
| 未決定 | バックログに可視化・常時最新化。隠さない |
| 対象範囲 | 汎用コア。会社プロジェクト固有情報は持ち込まない（RAG設計のみ汎用パターンで内蔵） |

---

## DO / DON'T

**DO:**
- 未決定ノードだけをリサーチし、決定済みノードは再検討しない
- 決定は Best of N（2〜3案）→ 人間決定（AskUserQuestion）で行う
- 決定ログに「決定・理由・却下案」を記録する
- 文書は結論先行・表/mermaid・曖昧語禁止で整形する
- 未決定バックログを冒頭に可視化し、常時最新化する
- 出力先は Obsidian `${OBSIDIAN_VAULT}/00-Inbox/`

**DON'T:**
- 曖昧なまま設計書を出力しない（未決定ノードを隠さない）
- 1ループで複数の未決定ノードを同時判断しない
- 会社プロジェクト固有情報を汎用コアに入れない
- 詳細WBS（タスク分解・見積り）まで本スキルで作らない（`/impl-doc` へ委譲）
- 曖昧語（「〜の方が良い」「適切に」等）で決定を濁さない

## やってはいけないこと（悪い例 → 良い例）

| やってはいけない | 悪い例 | 良い例 |
|------------------|--------|--------|
| 決定を明示せず進める | 「検索はベクトル検索の方が良さそう」 | 「検索方式=ベクトル検索（埋め込み×コサイン）を決定。却下: BM25単独（語彙ミスマッチ）」 |
| 曖昧語で濁す | 「バランスよく設計する」 | 「RAG回答の保証: 根拠なき回答は『根拠なし』と明記（閾値: 確信度<0.5で抑制）」 |
| 未決定を隠す | 設計書に「運用は後で決める」とだけ書く | 未決定バックログに「運用方式: 未決定（要リサーチ）」として冒頭可視化 |
| 決定済みを再検討 | 前のノードで決めた技術を後段で無言で変更 | 変更する場合も決定ログに「変更・理由」を追記 |
| 詳細WBSまで作る | タスク毎に時間見積りを本スキルで書く | マイルストーンまで出力して `/impl-doc` に委譲 |

## 品質基準（完了判定）

- [ ] 未決定ノードが決定解決ループ（Best of N→人間決定→固定化）で解決された
- [ ] 決定ログに「決定・理由・却下案」が記録された
- [ ] 設計書が結論先行・表/mermaid・曖昧語禁止で整形された
- [ ] 未決定バックログが冒頭に可視化された

- [ ] 会社プロジェクト固有情報が汎用コアに入っていない（RAG設計のみ内蔵）
- [ ] 出力先が Obsidian `${OBSIDIAN_VAULT}/00-Inbox/` になっている

## 関連スキル（重複境界）

- `design-doc` — アイデア→設計書（質問テンプレ主体）。**決定解決ループ・低認知負荷原則を持たない**。本スキルは「決定を固める」点で上位互換。
- `impl-doc` — 設計書→実装計画（詳細WBS・見積り・リスク）。本スキルの **Phase 4（詳細WBS）はここへ委譲**。
- `domain-model` / `api-design` — DDD / API の縦割り設計。汎用アーキ/アルゴ選定には狭い。
- `session-kickoff` — PM/セッション管理（ゴール→WBS→リサーチ→引継ぎ）。アーキ特化の「認知負荷×決定解決」には特化していない。
- `ui-brief` — 設計書→UI設計ブリーフ。UIに特化。
