# session-kickoff — セッションキックオフ・オーケストレーター

本スキルは **1回の起動で「ゴール→プラン→引継ぎ→Go待ち」までを流すPM** である。
手打ちプロンプトを廃止し、品質・ループ防止・生産性を構造として組み込む。

**単一の真実（計画）**: 進行中タスクのプランは `~/.claude/plans/<task>.md`（生きた文書）。
新規起動でフル作成し、以降は `--replan` でインプレース更新。乱造しない。

**単一の真実（状態）**: セッション状態・再開判断は Obsidian `20-Areas/Claude-Code/session-router.md` + `sessions/<topic>.md`（1トピック=1ノート）。共有メモリ/context.md にはセッション状態を書かない。

---

## 起動モード（2種類）

### A. `initial`（新規タスクのキックオフ）— 既定
フェーズ0→8を流す。最後は Go待ち。

### B. `--replan`（進行中タスクのプラン改訂）
進行中タスクのプランを最新化する専用フロー。**新規Skillは作らない**。
`session-kickoff --replan <task>` で起動:

```
1. 状況把握 — 現在地と旧プランとの差分を確認
2. 新事実をプランに統合 — changelog に記録（新事実・決定ログを追記）
3. 影響範囲を再分解 — 影響を受けるサブツリーだけ分解し直す
4. 必要なら限定リサーチ — 変更領域のベストプラクティスのみ再調査
5. プラン更新 → 全新規フェーズは Go待ち
```

**判断ルール（インクリメンタル or フル再キックオフ）**:

| 事象 | 対処 |
|------|------|
| 局所的な新事実・小さなリスク（構造に影響しない） | `--replan` で該当箇所だけ更新＋ログ |
| 構造が変わる/新領域が加わる/方針転換 | `initial`（フル再キックオフ）で刷新 |

基準: 「分解のサブツリー1つ程度」なら更新。「全体の構成やゴールに波及」するならフル再キックオフ。

---

## フェーズ0〜8（initial）

```
session-kickoff 起動
  ├─ Phase 0 状況把握（branch/worktree/未コミット確認）      [Auto-Exec]
  ├─ Phase 1 ゴール設定（検証可能な合格条件へ変換）
  ├─ Phase 2 要望の明確化（不足は AskUserQuestion）
  ├─ Phase 3 タスク分解（WBS化 ＋ 各タスクに「想定コスト」ラベル）
  ├─ Phase 4 リサーチ（research-explorer をチャネル並列起動・隔離）
  │         └─ 各サブエージェントへ「タスクブリーフ」を渡す（予算+範囲）
  ├─ Phase 5 プラン策定（plans/<task>.md に書く）
  ├─ Phase 6 セッション分割・ブレイク判定（残量50-60%で切る）
  ├─ Phase 7 引継ぎ自動保存（plans/ + Obsidian sessions/<topic>.md + router）
  └─ Phase 8 Go待ち（実行は明示Goまで保留）★
```

## Phase 0: 状況把握（Auto-Exec — 確認なく即実行）

```bash
git branch --show-current        # 現在のブランチ
git status --porcelain           # 未コミットがあれば報告（他セッションの混在に注意）
git log --oneline -3             # 直近の履歴
```

- 新規タスクなら **起動前に礖打ち（会話のみ・コード書かない）** をすることを **{USER} に提案**。
- 「やってみて」「実装して」の合図を待ってから実装を開始する（Phase 8）。
- main直コミット禁止 → タスク用ブランチ/worktreeを切ってから。

## Phase 1: ゴール設定（検証可能な合格条件へ）

- 要望を **検証可能なゴール** に変換する: 「〇〇を追加」→「△△の入力を不正として弾き、テストを通過させる」。
- 弱い成功基準（「動くようにして」）は無限ループを生む。**強い成功基準が効率を決める**。
- ゴールは `plans/<task>.md` の冒頭に「合格条件（検証可能）」として書く。

## Phase 2: 要望の明確化

- 曖昧な点は勝手に解釈せず、前提を宣言する。
- 複数解釈がある場合・本質的に不足がある場合のみ **AskUserQuestion** で確認。
- 些細 / 明白な前提は推測せず軽く宣言して進む（必要なら確認）。
- **セッション命名の確定**: トピック/セッション名を決め、`claude -n <topic>`（/rename）と Obsidian ハンドオフ `sessions/<topic>.md` を対応付ける（1トピック=1ノート、日付散乱させない）。

## Phase 3: タスク分解（WBS化）

- ゴールを **WBS（Work Breakdown Structure）** に分解する。
- 各タスクに **想定コスト（S/M/L）** と依存関係をラベル付け。
- 次の構造を意識: 計画系フェーズは逐次=メインで / リサーチ・レビューのみ並列可能。
- 単一サブエージェントが抱えるタスクは **5〜6件まで**（公式推奨）。

## Phase 4: 並列リサーチ（コンテキスト隔離）

**リサーチが必要な場合のみ。** 次のチャネルを `research-explorer` で並列起動する:

| チャネル | 調査対象 | max_turns |
|---------|---------|-----------|
| official-docs | 公式Doc・リファレンス | 6 |
| github | リポジトリ・issue・PR | 6 |
| reddit | コミュニティ議論・実体験 | 6 |
| x | X/Twitter の動向 | 6 |

各 `research-explorer` 起動に **タスクブリーフ** を必ず添付する（契約）。詳細は FORMS.md の「タスクブリーフ」雛形を参照:

```markdown
## Objective（何を達成するか）
## Do（やること） — チャネル: 〇 / 調査項目: [具体的リスト]
## Don't（やらないこと） — 実装を始めない/範囲外を触らない/ソース無き主張は「未検証」
## Deliverable（戻す成果物） — 形式: 構造化サマリー（<=500トークン）/ 引用: 必ずURL
## 予算 — max_turns: 6 / 要約トークン上限: 500 / effort: low
```

- サブエージェントは **新鮮なコンテキスト** で起動 → メインの汚染を根本から防ぐ。
- 高出力タスク（ログ収集・大量Doc取得等）もメインでやらずサブエージェントへ。
- **引き継ぎが想定される調査**（→ `/mid-point` で次のセッションに実装を回す場合）は、タスクブリーフに
  `詳細保存先: ~/.claude/tmp/research/<topic>/` を明記し、生詳細（根拠URL・判断過程）をファイルに残させる。
  戻り値サマリーは従来通り <=500トークン。詳細の保存は `research-explorer` の任意契約（詳細保存先指定時のみ）。
- `research-explorer` が無い/不要な場合は、既存 `/research`（汎用ルーター）へ委譲してよい。
  （研究テーマ自体が目的の場合に使用。session-kickoff内での調査は `research-explorer` 優先）

## Phase 5: プラン策定

`plans/<task>.md` に次を書く（FORMS.md「プラン雛形」参照）:
- **frontmatter**: タスク名・作成日・状態（進行中）
- **version + changelog**（生きた文書の要。改訂のたびに追記）
- **ゴール・合格条件**（Phase 1 の成果）
- **WBS**（Phase 3 の成果）+ 各タスクのコスト・依存
- **新事実・決定ログ**（再発見を防ぐ）
- **セッション分割**（Phase 6 の成果）

## Phase 6: セッション分割・ブレイク判定

- **コンテキスト残量 50〜60% に到達したら、そこで強制ブレイク。**
  そこまで進んだ成果を Phase 7 で引継ぎとして保存し、新セッションで再開する。
  （手動 compact のタイミング判断は人間が必ず失敗する → フェーズ境界で自動ブレイク）
- WBS を複数セッションに分割する場合は、各セッションの境界を明記する。

## Phase 7: 引継ぎ自動保存（プラン更新 + Obsidianハンドオフ）

セッション境界・中断時は、新ハンドオフを乱造せず **2つの単一情報源をそれぞれ最新化** する:

1. **タスクの計画** `plans/<task>.md`: 立ち位置/完了/未完了/次にやること/開いたままの決定 を追記し、changelog に記録。
2. **セッション状態（Obsidian）**:
   - `20-Areas/Claude-Code/sessions/<topic>.md` をインプレース更新（無ければ `sessions/_TEMPLATE.md` から作成。ゴール/進捗/未完了/次アクション/決定/changelog）。
   - `20-Areas/Claude-Code/session-router.md` の該当行を更新（status flip。done なら「終了・done」へ移動）。

- セッション状態は共有メモリ / context.md に書かない（**並列セッション混在防止**）。
- 既存 `session-end`（git commit + mnemon capture）と連動して記憶保存。
- **00-Inbox 等の知識ノートは本文改変禁止**。更新は `20-Areas/Claude-Code/sessions/` と session-router.md のみ。

**任意タイミングの中継は `/mid-point` へ委譲**: 「調査→実装を別セッションに分けたい」「コンテキスト圧迫してきた」場合、
本フェーズのフローをそのまま `/mid-point`（調査レポートを Obsidian 00-Inbox/ にも保存する強化版）で実行してよい。
`/mid-point` は本 Phase 7 の任意タイミング版＋調査詳細の引き継ぎ保存を1コマンドで行う。

## Phase 8: Go待ち ★（最重要）

**実行（実装）は明示の Go まで開始しない。**
- 「実装して」「やって」「Go」の合図が出るまで、プラン提示と待機のみ。
- プランの提示は簡潔に。全体を読ませない（重要部分のみ表に出して確認）。

---

## タスクブリーフ契約（委譲の必須フォーマット）

サブエージェントへ **必ず** タスクブリーフを添付する。3セクション + 予算:

| 項目 | 内容 |
|------|------|
| **Do / Don't** | やること・やらないことの明示。範囲外に触れない。ソース無き主張は「未検証」 |
| **予算** | `max_turns`（調査6/レビュー8）・コンテキスト上限・要約トークン上限（500）・`effort`（low/medium/high） |
| **Deliverable** | 戻す成果物の形式（構造化サマリー・URL引用） |
| **タスク数** | 単一エージェントで5〜6件まで |

---

## DO / DON'T

**DO:**
- ゴールを検証可能な合格条件に変換する
- リサーチ・レビューのみ並列（サブエージェント横並び）
- 各委譲にタスクブリーフ（範囲+予算）を厳密に添付
- コンテキスト残量50-60%で強制ブレイク→引継ぎ保存
- プランは生きた文書として `plans/<task>.md` をインプレース更新
- 実行は明示Goまで保留

**DON'T:**
- 明示のGoなしに実装を開始しない
- 計画系フェーズを並列化しない（逐次=メインで）
- 実験的エージェントチームを使わない（GH#23620 バグ・コスト・実験性）
- 新ハンドオフファイルを乱造しない（プランを最新化する）
- `/research` と重複する機能を作らない

- [ ] ゴール→分解→リサーチ→プラン→引継ぎ→Go待ちまで一連で流れた
- [ ] リサーチはサブエージェント並列・各々に範囲とトークン予算が明示された
- [ ] コンテキスト残量50-60%で強制ブレイク→引継ぎが自動保存された
- [ ] 実行は明示Goまで開始されなかった
- [ ] 既存 `/research` と重複していない
