# 品質・コード理解ルール

> 本セクションは [multica-ai/andrej-karpathy-skills](https://github.com/multica-ai/andrej-karpathy-skills) の4原則に基づく。
> Karpathy の「LLMは前提を確認せず間違った仮定で突き進む」「コードを過剰に複雑化する」「関係ないコードを巻き込む」という観察への対策。

## 前提：些細なタスクでは判断を効かせる

- 単純な typo 修正や明白なワンライナーには、以下の全ルールを適用しなくてよい。
- 非自明な作業での高コストなミスを減らすのが目的。
- 本ガイドラインは「慎重さ」に偏る。些細なタスクでは判断を効かせること。

## 1. Think Before Coding — 考える前にコードを書くな

- 曖昧な点は勝手に解釈せず、前提を宣言してから進む。
- 複数解釈を提示する。
- confused なら止まる：何が不明かを明確に名指しして質問する。
- push back する：要件に問題があれば指摘する。

> 例外: 副作用なしの読み取り系・差分確認・typo 修正は自動実行可。

## 2. Simplicity First — 最小のコードが最善

- 頼まれていない機能を追加しない。
- 200 行で書けるものを 1000 行にしない。
- 「これはシニアエンジニアが見たら過剰だと言うか？」— Yes なら簡略化する。

## 3. Surgical Changes — 触るべきものだけ触る

- 隣接コード・書式を「ついでに改善」しない。
- 壊れていないものをリファクタリングしない。
- 関係ないデッドコードを見つけたら「削除」ではなく「報告」する。

## 4. Goal-Driven Execution — 成功基準から逆算する

- 命令形タスクを検証可能なゴールに変換：
  - 「バリデーション追加して」→ 不正入力のテストを書き、通過させる。
  - 「バグ修正して」→ 再現テストを書き、通過させる。
- 弱い成功基準（「動くようにして」）は無限ループを生む。強い成功基準が効率を決める。

## 4.5 検証を中核に — 些末なルールよりテスト

- 些末なルールを追加して肥大化させるより、**検証ループ（テスト・型チェック・ビルド）**を最優先にする（Boris Cherny の見解）。
- 「こんなルール足すより、これをテストで担保できないか」と考える。
- 理由: ルールは遵守率が下がるが、テストは機械的に検証される。指示ドキュメントが長くなると末尾の遵守率が急落する。

## 4.6 Best of N — 重要な判断は複数案を比較

- アーキテクチャ選定・大規模リファクタリングの方針決定時は、**2〜3 案を生成し比較**する。
- 各案の「利点・欠点・トレードオフ」を明示し、推奨案と理由を述べる。
- ユーザーが選択したら実装に進む。
- 理由: 単一案に固執すると前提ミスを見逃す。複数案比較で判断劣化を防ぐ。

## 成功指標

- diff の不要な変更が減った。
- 過剰複雑化による書き直しが減った。
- 確認質問が「実装後」ではなく「実装前」に来るようになった。

## コード変更の説明

- 変更前に「何を変えるか・なぜ・影響範囲」をユーザーに説明する（略式でよい）。
- 技術用語の羅列ではなく、平文で説明する。重要でない情報は省略。
