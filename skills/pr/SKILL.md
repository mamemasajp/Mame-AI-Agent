# /pr — ベストプラクティス準拠PR作成

## 概要

push済みの機能ブランチから、**自己レビュー済み・説明充実**のPull Requestを作成する。
性質上、PRは「まだ上がっていない仕事」ではなく「レビュアーへの提供物」。手続きが短く**説明義務が大きい**。

本スキルは次の2点を保証する：
1. **提出前自己レビュー** — diffを読んでから出す。出してから気付いて修正→再pushの往復を減らす
2. **日本語の説明文** — 概要・背景・変更内容・検証方法・レビュー観点をテンプレから自動生成

## トリガー

- ユーザーが「PRして」「プルリク作って」「リクエスト上げて」等と発言
- `/session-end` 後の自然な続き
- **PR作成はユーザーの明示指示があった場合のみ**（`rules/02-git-workflow.md`）。本スキルの呼び出し自体が明示指示とみなせる

---

## フロー（4 Phase）

```
/prトリガー（ブランチpush済み前提）
    ├─ Phase 0: 前提チェック（2秒）— branch / upstream / gh auth / 未コミット有無
    ├─ Phase 1: 差分理解（8秒）— main..HEAD のdiffを読み、意図・影響範囲を分解
    ├─ Phase 2: 自己レビュー（10秒）— 検証実行 + 不要物チェック
    └─ Phase 3: PR作成（10秒）— 本文生成 → gh pr create → URL出力
```

---

## Phase 0: 前提チェック

```bash
git branch --show-current                      # 現在ブランチ（feature/xxx であること）
git rev-parse --abbrev-ref @{u} || echo "NO_UPSTREAM"   # upstream有無
gh auth status 2>&1 | head -3                  # ghログイン有無
git status --porcelain                         # 未コミット変更有無
git rev-list --count @{u}..HEAD || echo 0      # push済みか（先行コミット数）
```

**チェック項目と対処:**

| 状態 | 対処 |
|------|------|
| mainブランチ上 | PR対象ブランチに切替えを促す（rules: main作業禁止） |
| 未コミット変更あり | 先に commit するか、なぜ未コミットかユーザーに確認 |
| upstream未設定 | `git push -u origin <branch>` を促す |
| gh未ログイン | `gh auth login` を指示（ユーザーが実行） |
| 先行コミット0 | まだpush前。「pushしてからでないとPRできない」旨を告げる |

**PRには「push済みの可視差分」が必要。** push前に同名ブランチのPRが作れないため、原点に戻って push を確認する。

---

## Phase 1: 差分理解

diffを読み、PRタイトルと説明の材料を作る。**merge先は main を基本**とする。

```bash
BASE=${BASE:-main}                              # 必要なら環境変数で上書き
git fetch origin $BASE -q 2>/dev/null || true
git diff $BASE...HEAD --stat                    # 変更ファイル一覧
git log --oneline $BASE..HEAD                   # このブランチのコミットで意図を読む
git diff $BASE...HEAD -- <重要ファイル>          # 核心ファイルの実差分を読む
```

- `$BASE...HEAD`（トリプルドット）で、main由来の重複変更を除いた**純粋な本ブランチ差分**を見る
- ファイル名・コミットメッセージ・実差分の3点から「何を・なぜ変えたか」を把握
- **分からなかったら解釈で進めない。** 変更が多すぎる・意図不明ならユーザーに確認

---

## Phase 2: 自己レビュー + 検証

出す前の最後の門。**Evidence Before Claims**（`rules/03-session-lifecycle.md`）に従い、検証結果をPR本文に載せる。

### 2-1: 論理的ブレがないか

| 観点 | チェック |
|------|----------|
| 不要な差分 | 本題と無関係のファイル・書式変更・リネームが混ざっていないか |
| デバッグ残骸 | `console.log`・`print`・コメントアウト・TODOが残っていないか |
| 秘密情報 | シークレット・APIキー・`.env`・絶対パスが混入していないか（`rules/01-safety.md`） |
| 破壊的変更 | 既存動作を変える変更なら、その影響範囲がタイトル/説明に明記されているか |
| リンキング | 対応するIssue番号 `#n` ・関連PRを本文で参照できるか |

### 2-2: 検証実行（可能なら）

```bash
# リポジトリに合わせて（存在すれば）
test/build/lint の該当コマンドを実行
```

- **検証コマンドが存在すれば必ず通す**（`rules/03-session-lifecycle.md`：L1静的/L2動的/L3整合性）
- テストが無い場合も「テスト無し」と本文に明記し、代替検証（`bash -n` 等）があれば実行
- 検証結果は **PR本文の「検証方法」セクションに実結果として記載**（"passes" 等の実測値）

---

## Phase 3: PR作成

### 3-1: タイトル

`<prefix>: <理由>、<内容>` — 既存コミット規約（`rules/02-git-workflow.md`）と統一。

| prefix | 用途 |
|--------|------|
| `feat` | 新機能・新規追加 |
| `fix` | 不具合修正 |
| `refactor` | リファクタリング（仕様不変） |
| `docs` | ドキュメント |

例: `feat: PR自動作成のため、/prスキルを追加（add /pr skill for automated PR creation）`

### 3-2: 本文テンプレート

```markdown
## 概要
<このPRが何をするのか、1〜3文で。何を・なぜ>

## 背景
<なぜ必要か。既存の課題・制約・関連文脈>

## 変更内容
- <変更項目を箇条書き>
- <必要ならファイル単位で>

## 検証方法
- <実行したコマンドと結果を実測値で>
- [ ] テスト実行: `pytest` → 12 passed
- [ ] 確認方法: <レビュアーが確認すべき手順>

## レビュー観点
<特に見てほしい箇所・課題・判断ポイント>

## 関連
- closes: #<issue>
- 関連PR: #<n>
```

- **「変更内容」はファイル名だけでなく「何が変わったか」を書く**
- **「レビュー観点」を必ず書く** — 推測でなく、自分が迷った点・妥協点・要判断箇所を明示する
- `.github/PULL_REQUEST_TEMPLATE.md` が存在すれば、テンプレートに優先して従う

### 3-3: 作成

```bash
gh pr create --base $BASE --title "<タイトル>" --body "<本文>"
```

- **ブランチ名とprefixは自動で読めるが、タイトル・本文の日本語文は必ずHuman確認を挟む**（ユーザーが修正したい場合がある）
- **merge戦略**: squash merge を推奨する注記を本文末尾に添える（トピック単位の歴史、surgical changes 維持）
- 作成後 `gh pr view` でURLを出力・ユーザーに提示

### 3-4: 作成後

```bash
gh pr view --json url,number,state,headRefName  # URL確認
```

- PR URLをユーザーに提示
- 「draftで出すか・すぐレビュー募集か」はユーザーに確認してから最終決定（デフォルトは手動でReady）

## ベストプラクティス（教育）

PRは単なる「変更の提示」でなく **レビュアーの判断材料**。ここが心得えると差がつく。

1. **1PR=1トピック**
   - 大きいPRほどレビュー精度が落ちる・指摘が遅れる。論理的に分離可能なら分割を提案
   - 目安: 変更が広範・複数関心事なら分割し、それぞれ `/pr` を実行
2. **タイトルで結論を先に**
   - タイトルを読むだけで「何が変わったか」が分かるのが理想。`prefix: 理由、内容` で統一
3. **「なぜ」を書く**
   - レビュアーはコード全体を知らない。「背景」を書けば妥当性判断が速くなる。不要な質問往復を防ぐ
4. **自己レビューを義務に**
   - 提出前に自分のdiffを全文読む。機械的ミス（typo・不要ファイル・テスト漏れ）の大半はここで消える
5. **検証結果を証拠として添える**
   - 「動くはず」ではなく「テスト12件パス」を書く。レビュアーの再検証コストを下げる
6. **関連をリンクする**
   - Issue `#n`・関連PR・仕様書を本文で参照。文脈を追わせない
7. **draft→ready を使う**
   - 完成度が厳しいPRはdraftで出して方向性だけ確認する。作りかけを見せるのはむしろ効率的
8. **mergeはsquash**
   - 個人/チーム内なら squash merge でトピック単位に歴史を畳む。レビュー途中の細かい修正がhistoryに残らない
9. **レビュー指摘に速やかに返答**
   - 指摘コメントへの返信はコメントで行う（コード修正だけして黙らない）。コンテキストを共有する
10. **mainに直接mergeしない**
    - mainは常にリリース可能に保つ（`rules/02-git-workflow.md`）

## DO / DON'T

**DO:**
- Phase 0前提チェックを必ず通す（branch / upstream / auth / 未コミット）
- main..HEAD の純差分を見る（トリプルドット）
- 検証コマンドがあれば実行し、**実結果**を本文に載せる
- タイトル・本文を作成してから **ユーザーの文言確認** を挟む
- squash merge 推奨を注記する
- PR URLを提示する

**DON'T:**
- 力を入れずに `gh pr create --fill` だけで流さない（本文が差し替え・説明不足になりがち）
- 未コミット・未pushの状態でPRを作ろうとしない
- 解釈不明な変更を勝手に読み替えて説明を作らない（確認する）
- 秘密情報・デバッグ残骸をPR本文やdiffに残さない
- 環境変数・個人ローカル設定をPRに含めない

## 品質基準

- [ ] 前提チェック通過（branch / upstream / gh auth / clean）
- [ ] `main...HEAD` 差分を把握して自己レビューした
- [ ] 検証（該当があれば）を実行し実結果を本文に記載
- [ ] タイトル `prefix: 理由、内容` 形式
- [ ] 本文に 概要/背景/変更内容/検証/レビュー観点 が揃っている
- [ ] squash merge推奨の注記あり
- [ ] PR URLをユーザーに提示
