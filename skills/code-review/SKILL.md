# /code-review - コードレビュー卓越性

## 概要
コードレビューを **ゲートキーピングからナレッジシェアリング** へ転換。建設的フィードバック・体系的分析・協調的改善の3本柱で実施。

## レビュー観点 (優先度順)

| 優先度 | 観点 | チェック項目 | 目安 |
|--------|------|-------------|------|
| **P0: Correctness** | 正しさ | 要件充足・バグなし・エッジケース・競合・冪等性 | 必須 |
| **P1: Security** | セキュリティ | 入力検証・認証認可・暗号化・秘密情報・インジェクション | 必須 |
| **P2: Maintainability** | 保守性 | 命名・関数サイズ・依存・テスタビリティ・ドキュメント | 高 |
| **P3: Performance** | 性能 | N+1・無駄な計算・メモリ・キャッシュ・DBインデックス | 中 |
| **P4: Style** | スタイル | 規約準拠・フォーマット・インポート順・未使用 | 低 |

## レビュープロセス

### 1. 事前準備 (Author)
- [ ] 自己レビュー完了 (diff確認・テスト実行・Lint/TypeCheck通過)
- [ ] PR説明: 何・なぜ・どう・影響範囲・テスト方法
- [ ] 関連Issue/Design Docリンク
- [ ] スクリーンショット・動画 (UI変更時)

### 2. レビュー実施 (Reviewer)
```
1. 全体像把握 (30秒): ファイル構成・変更規模・リスク領域
2. P0-P1 優先レビュー: 正しさ・セキュリティ
3. P2-P3 詳細レビュー: 設計・性能・保守性
4. P4 スタイル: 自動化ツール任せ・指摘最小限
5. フィードバック分類・優先度付け
6. 承認 / 条件付き承認 / 要修正
```

### 3. フィードバック分類

| ラベル | 意味 | 対応 |
|--------|------|------|
| 🔴 **Must Fix** | バグ・セキュリティ・要件不備 | マージブロック |
| 🟡 **Should Fix** | 設計改善・性能・保守性 | 次回コミットで対応 |
| 🟢 **Consider** | 代替案・リファクタリング提案 | 任意・議論歓迎 |
| 🔵 **Nitpick** | スタイル・タイポ・微細 | 自動修正・無視可 |
| 💬 **Question** | 理解確認・意図質問 | 回答待ち |

### 4. フィードバック記述テンプレート

```markdown
## 🔴 Must Fix: [ファイル:行]
**問題**: 具体的に何が間違っているか
**影響**: 何が起きるか (バグ・脆弱性・仕様違反)
**修正案**: どう直すべきか (コード例歓迎)
**参考**: 関連ドキュメント・過去事例
```

## コマンド

### レビュー実行
```
/code-review start --pr=123 --reviewer=@me
/code-review checklist --pr=123 --level=P0,P1
/code-review comment --file=src/auth.ts --line=45 --level=must-fix --msg="..."
/code-review approve --pr=123 --conditional="Should Fix対応後"
/code-review request-changes --pr=123 --summary="P0: 認可チェック漏れ"
```

### 自動化連携
```
/code-review automate --enable=lint,typecheck,test,security-scan
/code-review gate --pr=123 --require=P0,P1 --auto-merge=on-approve
```

### 分析・改善
```
/code-review stats --period=month --team=backend
/code-review patterns --anti-patterns --period=quarter
/code-review calibrate --reviewers=@team --session=30min
```

## レビュー品質指標

| 指標 | 目標 | 測定 |
|------|------|------|
| **レビュー時間** | < 2時間 (小) / < 1日 (大) | PR作成→初回レビュー |
| **指摘密度** | 1-3件 / 100行 | 総指摘数 / 変更行数 |
| **Must Fix率** | < 10% | Must Fix / 総指摘 |
| **再レビュー回数** | ≤ 2回 | 承認までの往復 |
| **知識共有度** | > 30% Consider/Question | 学び・議論の割合 |

## アンチパターン・回避

| アンチパターン | 症状 | 対策 |
|--------------|------|------|
| **LGTM駆動** | 中身見ずに承認 | チェックリスト必須・最低レビュー時間 |
| **ニットピック地獄** | スタイル指摘過多 | 自動化・Nitpickラベル・無視ルール |
| **設計議論迷子** | PRでアーキテクチャ議論 | 事前Design Doc・別スレッド |
| **知識独占** | 特定人しかレビューできない | ペアレビュー・ローテーション・ドキュメント化 |
| **フィードバック放置** | 指摘に返信なし・放置 | SLA設定・リマインダー・エスカレーション |

## ツール連携推奨

| ツール | 役割 |
|--------|------|
| **GitHub/GitLab PR** | 基盤・コメント・承認フロー |
| **Biome/ESLint/Prettier** | スタイル・フォーマット自動化 |
| **TypeScript/tsc** | 型チェック必須化 |
| **Semgrep/CodeQL** | セキュリティ・バグパターン自動検出 |
| **Pact/Schemathesis** | 契約テスト・破壊的変更検知 |
| **ReviewDog/CodeRabbit** | 自動コメント・要約・優先度付け |
